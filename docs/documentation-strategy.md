# Documentation Strategy (Ruby Projects)

Preferred layout and placement rules for documentation across Ruby gems and projects. Applies to single-gem repos and monorepos alike — in a monorepo, all paths below are relative to `gem/<gem-name>/` rather than the repo root, and the monorepo's top-level `README.md` is a "this is a monorepo" pointer.

## Layout

**Root (or gem root):**

| File | Status |
|---|---|
| `LICENSE` | Mandatory |
| `README.md` | Mandatory |
| `SECURITY.md` | Mandatory |
| `ROADMAP.md` | Optional |
| `DESIGN.md` | Optional — usually a thin pointer into `docs/` |
| `CHANGELOG.md` | Optional |
| `CONTRIBUTING.md` | Optional |

Avoid scattering further markdown at the root. If a document accumulated there because there was no `docs/` tree yet, the right fix is to stand up the tree and move it in.

**`docs/`** — authored documentation aimed at gem consumers. Rendered to GitHub Pages via `mkdocs` (Material theme). Wired into `mkdocs.yml`'s `nav:`.

**`docs/reference/`** — canonical primary-source material. Specifications, blueprints, state machines, load-bearing design principles. Cited by other docs and by code review; not read top-to-bottom.

**`docs/reference/api/`** — YARD output. Auto-generated by `rake docs:generate`. Never edited by hand.

## Placement rule

> **`docs/` is read. `docs/reference/` is cited.**

Test for a new file: will another doc, ADR, code review, or external reader *cite this by section anchor*, or will a reader work through it linearly to *learn how to use the gem*?

- Cited → `docs/reference/`
- Read → `docs/`

This replaces the older "consumer vs contributor" criterion, which broke down as soon as power users started reading the canonical design docs and contributors started using consumer guides. Content kind (cited vs read) is sharp; audience is fuzzy.

### Examples

| File | Location | Why |
|---|---|---|
| `getting-started.md` | `docs/guides/` | Tutorial — read top-to-bottom |
| `architecture.md` | `docs/` | Narrative explanation |
| `wallet-events.md` | `docs/` | Subsystem how-it-works |
| `schema.md` | `docs/reference/` | Canonical design statement, cited by ADRs and code |
| `principle-of-state.md` | `docs/reference/` | Load-bearing principle deferred to by other docs |
| `action-lifecycle.md` | `docs/reference/` | State-machine reference — jumped into by section |
| YARD output | `docs/reference/api/` | Generated |

## Reference subtypes

Content in `docs/reference/` comes in three flavours with different editorial handling:

**Internal blueprints** — your canonical truth about *this gem* (`schema.md`, `principle-of-state.md`, lifecycle references). Default to full mkdocs nav inclusion under a "Reference" section.

**Vendored upstream specs** — third-party content kept locally for offline / version-pinned access (e.g. a verbatim copy of a BRC). Include a "vendored from `<upstream>` at `<ref>`" admonition at the top. Include in nav, but in a sub-section that makes the vendored status clear ("External specs" or similar), so it doesn't read as authored content.

**Outbound drafts** — content you've authored that's destined for a *different repo* (e.g. a draft BRC). These belong upstream once submitted. While drafting, stage them under `docs/reference/drafts/` and **omit from `mkdocs.yml` nav**. The file still renders if linked directly, but doesn't appear in the sidebar where it would mislead a visitor about gem behaviour. On submission, replace the local file with a link to the canonical upstream version.

## Nav inclusion is per-file

A file under `docs/` does not automatically appear in the mkdocs sidebar — `nav:` in `mkdocs.yml` is opt-in. Three states per file:

| State | URL works | In search | In sidebar |
|---|---|---|---|
| Not in `docs/` | no | no | no |
| In `docs/`, omitted from `nav:` | yes | yes | no |
| In `docs/`, listed in `nav:` | yes | yes | yes |

Default reference content to the third state. Use the second for draft / staging material that should be cite-able by URL but not promoted in the consumer sidebar.

## Migration

Rationalisation is organic, not big-bang. Triggers for moving content:

- A new file is being created — place it correctly first time.
- A file is being substantially edited — move it as part of the edit if currently misplaced.
- A reader gets lost looking for a thing — fix the placement of the thing they were looking for, not the wider tree.

A repo can sit half-migrated indefinitely. The goal is convergence over time, not a clean sweep.

## Out of scope

JavaScript and TypeScript projects have different documentation conventions (TypeDoc HTML output, README-driven flat layouts, monorepo tooling like Nx/Turbo). This guide is for Ruby gems and Ruby projects only.
